# 性能排查与优化（2026-10-28）

本轮先把原工作区保存为 `26479ea5`，再修改代码。重点是消除预览、缩略图和导出的重复解码、临时对象与传输开销。没有新增业务入口、依赖或公共 Rust DTO，也没有调整内存上限、授权复核间隔、像素门槛或用户工程。

## 已确认问题与本轮改动

| 范围 | 源码依据与原因 | 改动及边界 |
|---|---|---|
| 视频预览、同素材跳切导出 | `packages/classic-visual-renderer/src/decoder.mjs` 对所有递增时间复用迭代器。剪辑从同一长源的前部跳到后部，仍会解码被剪掉的中间帧。 | 目标超过当前已观察帧的结束时间 2 秒时重新定位，保留同一个 Input、已核验资源与解复用状态。短距离追帧继续复用；覆盖目标的 VFR 长帧不重开；倒退、EOF 与实际 PTS 检查继续生效。 |
| 缩略图首次可见响应 | `source-art/service.ts` 每个已显示素材定时复核授权；`source-art/cache.ts` 原先将复核与新可见请求按同一 FIFO 排队。新内容可能等待多项复核。 | 单解码信用和取消确认不变。新可见请求优先；最多连续三个前台加载后服务一个等待中的复核，防止授权任务饥饿。已运行任务不抢占。 |
| 缩略图主线程分配 | `allocateArt` 使用正则将 JPEG 十六进制字符串拆成逐字节数组，再逐项解析；定期复核重复发生。 | 使用已有 `@noble/hashes` 的 `hexToBytes`。保留小写格式、长度、JPEG 标记、完整 SHA-256 和内存准入检查。 |
| 预览、缩略图与导出的源读取 | 共享 `verified-range-source.mjs` 对每个源字节分配子字符串并执行 `parseInt`。 | 原生 `Uint8Array.fromHex` 可用时使用原生转换；其余引擎直接转换已验证的字符码。源偏移、长度、EOF、取消与释放检查不变。 |
| 视频导出 | `host/video-browser.mjs` 经 Playwright 发送 RGBA 十六进制字符串，32 MiB 级原始帧会放大为双倍字符。 | 仅私有浏览器到 Node 的通道改用规范 Base64。Node 逐块恢复原有十六进制包，再交给同一个处理器和 Rust sink。仍为 64 KiB 每块、最多 16 块、逐块确认，新增整批固定帧身份检查。 |

浏览器解码使用仓库锁定的 Mediabunny 1.41.0，没有升级依赖。官方说明支持按时间定位及顺序迭代，且要求结束迭代器以释放资源；本轮按这一区别选择连续追帧或重新定位。[Mediabunny media sinks](https://mediabunny.dev/guide/media-sinks)。字节转换参考标准接口，并实测当前 Chromium；Node 中保留等价字符转换。[ECMAScript 字节编码接口](https://tc39.es/proposal-arraybuffer-base64/)。私有通道的调用边界是 Playwright 的页面函数桥接。[Playwright page.exposeFunction](https://playwright.dev/docs/api/class-page#page-expose-function)。

## 前后对比

同一台机器、Chromium `153.0.8010.12`、Node `24.19.0`。基线取自上述提交，候选直接读取修改后的源码。原始报告绑定各模块哈希、源视频哈希、运行时版本及候选差异哈希。

| 测量 | 修改前 | 修改后 | 实际范围 |
|---|---:|---:|---|
| 长源从 1.75 秒跳至 90.25 秒，直接 VideoFrame | 615.1 ms | 11.7 ms | 320×180、30fps、94 秒 H264，真实浏览器解码 |
| 同一跳转，单画布池 | 1049.9 ms | 8.0 ms | 同上，两个工作面的执行方式 |
| 同一跳转，旧画布池 | 678.5 ms | 6.2 ms | 同上，四个工作面的执行方式 |
| 跳转需要的范围读取 | 2623 次 / 3,045,382 B | 108 次 / 131,088 B | 三种执行方式均观察到相同计数 |
| 4K RGBA 桥接单帧，中位数 | 2365.2 ms | 1745.7 ms | 前/后/后/前四轮，每轮三帧，包含实际 Playwright 桥接与原生包接收，减少约 26.2% |
| 256 KiB 缩略图字节转换，每次中位数 | 43.53 ms | 0.62 ms | 两轮各 12 次，不含网络、JPEG 解码、宿主启动或授权 |

最后两项是局部阶段耗时，不能解释为完整导出或缩略图加载速度。Base64 仅减少浏览器通道约三分之一的字符；原生输出仍有原来的 RGBA 字节数、帧序和 SHA-256。

在冷启动、连续前进、远跳、继续前进和倒退五个位置，修改前后三种解码路径的实际 PTS 和逐帧像素哈希全部一致。导出桥接的完整原生字节哈希也一致。

独立 FFmpeg 对照仍失败：同一合成视频在直接帧路径的最大逐通道误差为 42–43，画布路径为 155–195，超过保留的 12 门槛。修改前后对应帧哈希相同，因此该差异同样存在于基线；具体转换或绘制原因尚未确定。报告保留失败及前期验证器错误，不能将前后相等当成独立像素验收通过。

实际原生流程复用了同一个合成工程、素材和固定修订。640×360、24fps、两个相距三秒的源片段共一秒，修改前后分别耗时 16.05 秒和 15.51 秒；各一次的观察不足以证明稳定吞吐提升。两个 MP4 的 SHA-256 相同，解码后的全部 RGBA 与 PCM 字节也相同。独立源帧对照的六个位置 MAE 为 15.79–19.90，仍超过 5 的门槛，因此原生输出已发布与独立像素验收失败同时记录。实际授权缩略图生成耗时 3.10 秒，输出 640×360 JPEG；这也说明字节转换的局部提速不等于冷加载已经足够快。

- 共享视觉测试 214 项、共享音频测试 74 项、来源图测试 5 项、相关 Web 测试 57 项通过。包括远跳/VFR/取消释放、字节一致性、非法 Base64、帧失效以及队列公平性。
- Web 在独立目录完成类型检查与生产构建。Rust 未改动，复用已验证的 CLI，SHA-256 为 `74f670cd51be9b5c1810c7e05d7df21bc75cf2a2130597eecd27fcb13e2a4821`；用该程序再次确认 184 个操作、12 个领域及生成契约一致。
- 架构测试 14 项、22 个模块的依赖检查、契约边界与 261 个 Web 源文件边界检查通过；依赖例外仍为零。
- 原有 `source-art` 全动线脚本停在已变动的媒体导入界面，并在清理时缺少 `expected_revision`；记录为失败，不能算本候选 UI 验收通过。复用其已完成的导入和合成数据库继续专项验证，没有重建用户工程。
- 实际新构建工作台观察到三个缩略图表面，点击播放后 3.31 秒出现画面，播放到一秒结束；页面异常和播放错误均为空。末尾脚本对两个同名“Scene sound ended”元素的断言产生选择器歧义，保留失败记录及截图，没有重复生成工程或播放来覆盖该失败。这是限定自动化观察与截图检查，不是完整 UI 或人工声画验收。

## 尚需继续解决的问题及顺序

| 顺序 | 当前证据 | 下一组改动方案与验收 |
|---|---|---|
| 0 | 独立浏览器源帧与原生导出的像素门槛均失败，前后字节一致只能排除本轮对应样例的输出变化。 | 复用原源帧、两个已完成 Job 和固定修订，分离解码颜色转换、画布绘制、源空间处理及编码误差；先解释独立预期与实际像素的差异，不提高门槛。完成后才能扩大渲染正确性声明。 |
| 1 | `picture-cache.ts` 启播串行等待当前及两个后续窗口，再预热两个解码器；首画面可能被后续窗口准备拖住。 | 分别记录授权、窗口发布、下载、解码和首声首画时延，再按播放缓冲信用拆分首画面与连续播放准备。不得用减少音频/视频缓冲掩盖卡顿；复用窗口和原 Job 验证冷播、热播、seek 及取消。 |
| 2 | `source_art_runtime.rs` 每次配置递归检查运行时文件，身份缓存 TTL 为 30 秒；每秒授权复核仍返回完整 JPEG。冷缩略图还需独立子进程。 | 先记录元数据扫描、身份捕获、授权、原生缓存命中与子进程启动的独立耗时，再决定是否需要批量授权回执或持久工作器。公共契约变更必须由 Rust 声明生成；不能以加长授权间隔或只用素材哈希代替授权。 |
| 3 | 4K 原始 RGBA 每帧为 33,177,600 B，即使本轮桥接提速，回读、跨进程转换和编码仍有较大成本。 | 后续评估经准入的二进制流或受限编码输出，但需贯穿 Rust sink、取消、背压、发布围栏及完整渲染器身份。不得恢复整帧 POST/Blob 所引起的隐藏复制。先用相同源和固定修订做整段导出吞吐、峰值 RSS 和独立像素/PCM对照。 |

| 5 | 本候选 Web 构建的工作台主块约 1.80 MB，gzip 约 508 KB，并触发构建体积提示。 | 测首开下载、解析及工作器初始化，再按实际工具使用拆分非首屏功能。保持共享运行时模块身份和授权资源加载，不把模块拆分本身当作速度提升。 |
